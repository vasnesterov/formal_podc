Nesting-Safe Recoverable Linearizability — PODC 2018

Hagit Attiya, Ohad Ben-Baruch, Danny Hendler. Nesting-Safe Recoverable Linearizability: Modular Constructions for Non-Volatile Memory. PODC 2018. DOI 10.1145/3212734.3212753. Formalized version: the authors' copy of the conference paper (10 pages, proofs included; no arXiv version). Copy of the paper: paper.pdf.

DOI · PDF · All differences · Lean source · GitHub

Verdict: ⚠️ Weakened. Lemma 1 holds, the recoverable read/write object (Lemma 2) and the recoverable compare&swap object (Lemma 3) satisfy NRL, and Theorem 4 (no wait-free recoverable test&set from read/write and test&set) is true, though its proof needed a repair. But the paper's only example of nesting, Algorithm 4, the "nesting-safe recoverable counter", does not satisfy NRL: its READ loses its partial sum when a nested recoverable READ crashes. No repair is proved, so the promised modular construction has no working instance.

Mistakes in the paper

❌ Algorithm 4, READ (the "nesting-safe recoverable counter")

Algorithm 4's READ is not NRL: when a nested recoverable R[i].READ crashes, the caller resumes after R[i].READ.RECOVER with its volatile partial sum val and loop index i lost, so a READ after a completed INC can return 0 (Alg4.read_not_nrl).

Impact. The counter is an example built on top of the other results, which do not depend on it, but it is the only nesting the paper shows. Repairing it requires a design change, e.g. keeping val and i in non-volatile memory; we proved no repair.

Details

READ sums R[1..N] with nested recoverable R[i].READ calls, keeping val and i in volatile variables. Under the paper's own model, a crash inside R[i].READ is recovered by R[i].READ.RECOVER, the innermost pending recoverable operation, and not by the counter's READ.RECOVER. The caller then continues line 14 with val and i lost. Counterexample with two processes and the most benign reset (volatile variables become 0): process 0 completes INC. Process 1 starts READ, reads R[1] = 1, and crashes inside R[2].READ. After R[2].READ.RECOVER it adds 0 to the reset val = 0 and returns 0.

✏️ Slips

  • Algorithm 4, INC.RECOVER. The test LI_p < 4 should be LI_p ≤ 4, so a crash just before line 4 makes INC return ack without incrementing (Alg4.inc_recover_not_nrl). The prose ("before line 4 – INC is re-executed") gives the intended test. Suppose process 0 crashes in INC when it is about to execute line 4, before invoking R[p].WRITE. Then LI_p = 4, and INC.RECOVER returns ack without incrementing. A later READ returns 0.

  • Lemma 2 (Algorithm 1). Written values must also differ from the initial value: the lemma is false if a process may write v₀, and the paper assumes only that "all values written to the object are distinct" (alg1_not_nrl_of_initial_rewritten). This is an implied assumption, satisfied by the paper's counter; lemma2 is proved with it. p writes 1 and crashes after its write to R. Then q writes v₀. p's recovery sees R equal to its saved old value, so it writes 1 a second time, and a reader sees 1, v₀, 1.

  • Algorithm 3, lines 26 and 28. They read await(R[p] = …) where they should read R[i], so as printed line 26 never terminates. Not formalized.

  • Lemma 3 (Algorithm 2). new must not be null, because the helping registers start at null. This is the paper's sentinel convention.

Proof gaps in true statements (1)Theorem 4

🔧 Theorem 4 (no wait-free recoverable test&set from read/write and test&set)

At each critical configuration the proof assumes "w.l.o.g. C₁∘p is p-valent" and crashes p, so the renaming can change the crashing process from round to round, and a process that crashes infinitely often does not contradict wait-freedom.

Impact. Statement true; repaired by always crashing the same process (theorem4, round).

Details

The concluding step needs "a crash-free execution of q" with infinitely many steps, which the infinite construction does not provide once the roles of p and q can swap.

Repair

Always crash the same process p. Whichever of D·p, D·q is p-valent, one of D·p·q·crash_p and D·q·p·crash_p is bivalent. The two configurations share a valency, because p's solo recovery cannot tell them apart. Each also inherits the valency of D·p or D·q, because q cannot see p's crash. We proved the theorem for all base objects that are read/write-like or test&set-like.

The formalizationmodel, Lean names of the results, trust

Model (Podc/Computability/Distributed/SharedMemory/NRL/Model.lean, a staged CSLib candidate).

  • Asynchronous shared memory with atomic base objects in non-volatile memory, for one implemented object O. Deterministic processes; the adversary chooses the schedule and the crashes. There is no randomness.

  • Individual crash-recovery. A crash erases the volatile variables, and the system restarts the process in Op.Recover with the same arguments and LI_p, the location it was about to execute. The crash and the recovery step form one event. After a primitive, the next location does not depend on the primitive's response; this is how we read LI_p, and Theorem 4 depends on it. After a crash the algorithm fixes the values of the volatile variables; the paper says "arbitrary values". This gives algorithms more power, so the impossibility is stronger, and the positive algorithms do not read their volatile variables before writing them.

  • NRL is Definitions 3–4: recoverable well-formedness, and linearizability of N(H) (the history without crash and recovery steps) in CSLib's sense. It is required for every finite history that satisfies the paper's assumptions on invocations (Env).

  • Wait-freedom is stated on infinite schedules: a process that never crashes again and takes infinitely many steps completes. This covers both the operation and its recovery function.

  • Nesting (Algorithm 4) is modelled by a separate concrete interpreter with two-level frames. A crash inside a nested operation runs the nested RECOVER, and the caller keeps only its return address.

Proof remarks. The paper's proofs of Lemmas 2 and 3 leave implicit that "linearize the recovered WRITE / failed CAS right before / after another process's step" is a speculative point. Our proofs linearize speculatively and retract the entry if the guess turns out wrong.
