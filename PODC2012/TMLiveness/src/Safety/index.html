import Papers.PODC2012.TMLiveness.Model -- CSLib candidate: Cslib/Computability/Distributed/TransactionalMemory/Safety.lean /-! # Safety properties of a TM: strict serializability and opacity (§2.4) A finite history `h` is * **strictly serializable** if there is a sequence `σ` of transactions — all committed ones and some commit-pending ones (which are then regarded as committed) — that respects the real-time order of `h` and in which every transaction is legal; * **opaque** if there is a sequence `σ` of *all* transactions of `h`, where every commit-pending transaction is completed by a commit or an abort and every live transaction by an abort, that respects the real-time order of `h` and in which every transaction is legal. A sequence `σ` of transactions is the paper's sequential history `H_s` (a sequential history equivalent to `h` is a concatenation of its transactions in some order). Legality is the sequential specification of read/write t-variables: a transaction reads, for each `x`, its own last write to `x` if any, and otherwise the value written to `x` by the last preceding committed transaction (or the initial value). Aborted transactions are checked but their writes are discarded. We also prove the basic facts on transaction bookkeeping used later: every reachable history is well formed (`WF`), the real-time order can be read off the `snap` field (`prec_of_snap`), opacity implies strict serializability (`EnsuresSafety.ss_of_opaque`), and the key combinatorial fact behind the impossibility proofs: a configuration of transactions that cannot be legally serialized
