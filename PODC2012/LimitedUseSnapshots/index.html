Limited-Use Atomic Snapshots — PODC 2012

James Aspnes, Hagit Attiya, Keren Censor-Hillel, Faith Ellen. Faster than Optimal Snapshots (for a While). PODC 2012. DOI 10.1145/2332432.2332507. Formalized version: the journal version Limited-Use Atomic Snapshots with Polylogarithmic Step Complexity, J. ACM 62(1):3, 2015 (author copy), together with the authors' erratum to it; numbering follows the journal version. The proceedings version has the same Algorithm 2 (its Lemmas 1–3 and Theorem 4). Copy of the paper: paper.pdf.

DOI · PDF · All differences · Lean source · GitHub

Verdict: 🛠️ Hard fix. The 2-component max array of Algorithm 2, the paper's key tool, is not linearizable as published in either version, an error the authors found and published in their erratum, which we confirm in Lean for k = 3; with the erratum's fix (an embedded MaxScan in MaxUpdate1) it is linearizable for every tree shape, but proving this takes a new linearization and criterion. Over atomic max arrays, Algorithm 3 is a linearizable (b−1)-limited-use snapshot with O(log² b log n) Updates and O(log b) Scans, and so is the multi-writer version (Theorem 5.1); the corrected max array keeps these bounds, and Theorem 4.2 needed new linearization points, because the paper's ones are wrong, a flaw not in the erratum. Joining the two halves is informal here, and Section 6 was not checked.

Mistakes in the paper

🛠️ Theorem 3.4 (Algorithm 2, linearizability of MaxArray_{k×h})

Algorithm 2 is not linearizable: with k = 3 (balanced tree, m = 2) and three processes, a slow MaxScan returns (1, 0) although MaxUpdate1(r, 1) completed before MaxUpdate0(r, 1) started (alg2_not_linearizable).

Impact. The authors found this error and published it in their erratum; we confirm it in Lean. The max array is the paper's key tool. The snapshot is left unproved as published, because the proof of Theorem 4.2 uses Theorem 3.4, but it is not refuted. The erratum's correction is linearizable (alg2_fixed_linearizable, for every tree shape). Lemma 3.5 is correct for Algorithm 2 as published (lemma_3_5), but it is not the cost of the corrected algorithm (lemma_3_5_erratum): MaxUpdate1 goes from O(log h) to O(log k log h), and Algorithm 3's O(log² b log n) per Update absorbs this.

Details

The execution is the erratum's:

  1. p₀ starts MaxScan, reads r.second = 0 (line 11) and r.switch = 0 (line 12), then pauses.

  2. p₁ runs MaxUpdate1(r, 1) to completion.

  3. p₂ runs MaxUpdate0(r, 1) to completion. It goes left at the root and sets the switch of the left child.

  4. p₀ resumes: it propagates its stale 0 into r.left.second, follows the new switch and returns (1, 0).

A linearization that lets the scan see 1 in the first component must put MaxUpdate0 before it, and by real-time order also MaxUpdate1. The Lean execution (badExec, 17 labels) is checked by decide. The non-linearizability proof is a short argument on an arbitrary candidate linearization.

The proof of Theorem 3.4 orders scans among themselves and each update against the scans, but never orders MaxUpdate0 against MaxUpdate1. The PODC 2012 version has the same Algorithm 2 and proof.

Repair

Line 9.5 of the erratum: MaxUpdate1 performs a MaxScan after its WriteMax. We prove this version linearizable (alg2_fixed_linearizable) with a new history-level criterion for max arrays (exists_isLinearization_maxArr). Each update goes immediately before the first scan that may see it, or last if there is none.

✏️ Slips

  • The erratum says the embedded MaxScan is added to MaxUpdate0(r, v) "after its WriteMax(r.second, v)". That line belongs to MaxUpdate1, which is what its own step-complexity paragraph uses (alg2_fixed_linearizable).

  • The proof of Theorem 5.1 says "op is always linearized after it performs Line 2". An operation can be linearized at another process's Update between its ReadMax and its WriteMax of GetTS. What the proof uses, that op is linearized after it begins, still holds (Snapshot.MW.theorem_5_1).

Proof gaps in true statements (2)Theorem 4.2 · Lemma 4.1

🔧 Theorem 4.2 (linearization points of Section 4.1)

Linearizing an Update at the first WriteMax(root.mr, ptr ≥ d) (d its own root pointer) is wrong, because another process may carry the new value to the root inside a smaller pointer c < d, and a Scan reading c returns the value before the Update is linearized (Snapshot.Counterexample.paper_linearization_points_fail, 3 processes).

Impact. The statement stands, with repaired linearization points (Snapshot.theorem_4_2).

Details

The false step is "if there is no Update by process j linearized before op, then count_j = 0".

Repair

Linearize an Update of process j with counter m at the first WriteMax(root.mr, c) with (root.seq[c])_j ≥ m.

🔧 Lemma 4.1

The proof does not justify that the parent's index at the invocation is at most the sum of the children's components (it follows from the monotonicity of seq along max-array states).

Impact. The statement stands, with the step added (Snapshot.lemma_4_1).

The formalizationmodel, Lean names of the results, trust

Model.

  • Asynchronous wait-free shared memory, CSLib Cslib.SharedMemory.Impl. Processes are deterministic and scheduled arbitrarily; a crash is a process that stops taking steps. There is no randomization. Linearizability is CSLib's (amended Herlihy–Wing).

  • Algorithm 2 is flattened over an arbitrary binary tree T : Shape. The leaves are the values of the first component, and the split m at a node is the size of its left subtree. This covers the balanced m = ⌈k/2⌉ and every unbalanced choice. The switches are atomic 1-bit registers. The MaxReg_h objects second are atomic max registers, as the paper uses them in Theorem 3.4; their access cost ch is a parameter of the step bounds.

  • Algorithm 3 is modelled over atomic max arrays, an atomic MaxReg at the root and register arrays, for any binary tree with the processes as leaves. Algorithm 4 is modelled over an atomic single-writer snapshot and an atomic timestamp max register.

  • CSLib has no composition theorem. "Algorithm 3 over the corrected Algorithm 2" therefore follows from the two linearizability results only by locality of linearizability, informally.

  • The bound b is not needed for linearizability with unbounded objects. Instead, limited_use shows that with at most b − 1 Updates every pointer and index stays < b.
