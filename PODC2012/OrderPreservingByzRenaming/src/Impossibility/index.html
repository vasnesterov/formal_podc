import Papers.PODC2012.OrderPreservingByzRenaming.Spec /-! # Impossibility of order-preserving renaming for `n ≤ 3t` (Theorem 46) **Three processes, one fault (Theorem 46).** We run a candidate protocol on an infinite *line* of nodes `0, 1, 2, …`; node `i` runs the code of process `i mod 3` with original id `i`, listens to node `i + 1` as process `(i + 1) mod 3` and to node `i - 1` as process `(i + 2) mod 3` (node `0` hears nothing from its left). For every `i`, the two adjacent nodes `i, i + 1` form a *lift*: the single Byzantine process `(i + 2) mod 3` simulates the rest of the line (FLM covering, `CoverSystem.decides_scenario_iff`). Applying the specification to the `M` executions `i = 0, …, M - 1` gives names `v₀ < v₁ < ⋯ < v_M` in `{1, …, M}`: a contradiction. Only the ids `0, …, M` are used, so the impossibility holds from the original namespace `{0, …, M}` (of size `M + 1`) into `{1, …, M}`, as in the paper. The paper uses a ring of `M + 1` processes; with process-specific code (CSLib's protocols may depend on the process) a ring would need length divisible by 3, the line avoids this. **General `n ≤ 3t`.** As in the paper, three processes simulate the `n`-process system (CSLib's `GroupSim`): process `i ∈ Fin 3` simulates the processes with index `≡ i (mod 3)`, giving the simulated process with index `k` the id `x · n + k`, where `x` is the simulator's id; the simulator decides the name of one of its simulated processes.
