import Papers.PODC2020.StoreCollectChurn.Spec /-! # The CCC store-collect algorithm (Algorithms 2–3) in a static system This file models the *Continuous Churn Collect* (CCC) algorithm of Section 4 of [Attiya, Kumari, Somani, Welch, *Store-Collect in the Presence of Continuous Churn with Application to Snapshots and Lattice Agreement*, PODC 2020, arXiv 2003.07787v3] for **static executions**: all `n` nodes (`Fin n`) are initially in the system (`S₀ = Fin n`), and no `ENTER`, `LEAVE` or `CRASH` event ever occurs. This is a special case of the model of Section 3, enough to refute the paper's regularity claim (see `CCCCounterexample.lean`). ## Why Algorithm 1 can be omitted Every handler of Algorithm 1 is triggered either by an `ENTER`/`LEAVE` event or by the receipt of an `enter`, `enter-echo`, `join`, `join-echo`, `leave` or `leave-echo` message, and these messages are only broadcast by handlers of Algorithm 1. In a static execution none of them ever fires, so `Changes` keeps its initial value `{enter(q) | q ∈ S₀} ∪ {join(q) | q ∈ S₀}`, the derived variables are constant, `Present = Members = S₀`, and `|Members| = n` (`numMembers`). ## Model * Times are natural numbers; the maximal message delay `D` is a parameter. * Each event (an invocation `COLLECT_p` / `STORE_p(v)` or the receipt by `p` of the broadcast number `k`) is processed atomically by the corresponding handler (Lines 26–54), which may broadcast messages (the store handler of Algorithm 3 broadcasts two messages in one step) and may produce a response (`ACK_p` / `RETURN_p(V)`). * Broadcast is reliable and FIFO, every node (including the sender) receives every broadcast, with a delay in `(0, D]` (Section 3); see `Admissible`. ## Two charitable repairs of the pseudocode (deviations from the paper) 1. **`is_joined` of the initial members.** Algorithm 1 initializes `is_joined` to `false` for every node, and only Line 12 sets it to `true`; read literally, a node of `S₀` would never answer collect queries (Line 52) nor acknowledge stores (Line 49), and no operation could ever terminate in a static system. Since the nodes of `S₀` are joined from time `0` (Section 3), we initialize `is_joined = true` for them. 2. **Messages of a finished phase are ignored.** The client handlers (Lines 30, 43) only test `t = tag ∧ q = p`. Since a collect operation uses the same `tag` for its collect phase and its store-back, read literally a late `collect-reply` received during the store-back would increment the store-ack counter, and late `store-ack`s received after the response would "return" again. We let a client act on a `collect-reply` only during the collect phase of a pending collect, and on a `store-ack` only during a store phase (store operation or store-back) of a pending operation. Both repairs only make the algorithm better behaved; the counterexample refutes the repaired algorithm, hence the paper under any reading of the pseudocode. The local variable `optype` of Algorithm 2 is subsumed by `NodeState.phase` (`optype = collect` iff the phase is `collect` or `storeBack`). -/ namespace Podc.StoreCollectChurn.CCC variable {n : ℕ} /-! ## Views (Section 4, Definition 1) -/ /-- A view of CCC: a set of triples `⟨q, v, sqno⟩` (node id, value, sequence number) without repetition of node ids, represented as a list.
