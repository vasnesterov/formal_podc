Byzantine Vector Consensus in Complete Graphs — PODC 2013

Nitin H. Vaidya, Vijay K. Garg. Byzantine Vector Consensus in Complete Graphs. PODC 2013. DOI 10.1145/2484239.2484256. Formalized version: arXiv 1302.2543 v1 (full version with appendices); numbering follows it. Copy of the paper: paper.pdf.

DOI · arXiv · PDF · All differences · Lean source · GitHub

Verdict: ⚠️ Weakened. The main contribution stands: Theorems 1–5 and Lemma 1 hold, so exact BVC in synchrony is solvable iff n ≥ max(3f+1, (d+1)f+1), and approximate asynchronous BVC needs n ≥ (d+2)f+1 and is achieved by the paper's algorithm, given the AAD exchange primitive. The tight bounds for restricted algorithms announced in the abstract are lost: the synchronous necessity in Theorem 6 (Section 4, stated without proof) is false for the class as defined, though likely true for the intended hull-preserving iterative class. The asynchronous necessity has no argument and is unchecked, and only the sufficiency halves survive, the asynchronous one after a one-constant change to Step 2.

Mistakes in the paper

❌ Theorem 6, synchronous necessity (restricted algorithms need n ≥ (d+2)f+1)

The necessity claim is false as stated: for n = 4, d = 2, f = 1 (where (d+2)f+1 = 5) a restricted algorithm whose vector state encodes the received inputs solves even exact BVC in two rounds (theorem_6_sync_necessity_false, round-independent: theorem_6_sync_necessity_false').

Impact. The definition is under-specified, so the tightness claimed for restricted synchronous algorithms fails for the class as defined. The claim is likely true for the intended hull-preserving iterative class, but we formalized nothing under such a reading. Section 4 states it without proof, and Theorems 1–5 and Lemma 1 do not depend on it.

Details

Section 4 defines the restricted synchronous structure only as "send your vector state to everybody, then compute the new state as a function of the old one and the received vectors". But the update function is unrestricted, and one vector of reals can encode any finite amount of real data. So the state can carry a full-information history. The algorithm: in round 1, store the encoded vector of received inputs. In round 2, for each k, take the majority of the values for k relayed by the three other processes (OM(1)), then output the chosen point of Γ. It is a restricted algorithm. The claim presumably needs an extra restriction that the paper does not state, e.g. that the new state lies in the hull of the received states.

Our restricted class lets the update depend on the round number t. This is harmless: in synchrony processes know t, and the paper's own algorithm stops after a fixed round. A second counterexample does not use t at all: inputs lie in the box [0,1]², encodings lie outside it, so the own state tells the rounds apart. (theorem_6_sync_necessity_false, round-independent: theorem_6_sync_necessity_false')

✏️ Slips

  • Theorems 4 and 5 ("necessary and sufficient"): Theorem 4 fails for inputs of width ≤ ε. Theorem 5 assumes known bounds [ν, U]^d, and with U − ν ≤ ε approximate BVC is trivial for every n (ownInput_solves_of_narrow). So the pair is tight only when U − ν > ε; theorem_4 needs inputs of width > ε, as in the paper's own 4ε inputs.

  • The round count 1 + ⌈log_{1/(1−γ)}((U−ν)/ε)⌉ is meaningless for U = ν and negative for U − ν < ε. Read it as 1 + ⌈·⌉₊, which works (rounds_spec).

Typos

  • Section 4: "the proof of correctness … is similar to the proof of Theorem 4" should say Theorem 5.

Proof gaps in true statements (2)Theorem 6, asynchronous sufficiency · Theorem 4

🔧 Theorem 6, asynchronous sufficiency (Step 2 under-specified)

The paper's Step 2 "analogous to Section 3.2" averages over subsets of B_i of size n − f, but here |B_i| = n − f, so Z_i is a single point and two correct processes need not share a point of Z.

Impact. Sufficiency holds for n ≥ (d+4)f+1 with a repaired Step 2 (theorem_6_async).

Details

The paper's argument (a common point z_ij) breaks. Section 4 says the proof relies on |B_i ∩ B_j| ≥ (d+1)f+1; it needs a common C ⊆ B_i ∩ B_j of the subset size used in Step 2.

Repair

With subsets of size n − 3f, or any s with (d+1)f < s ≤ n − 3f, the argument goes through and gives sufficiency for n ≥ (d+4)f+1 (theorem_6_async).

🔧 Theorem 4 (scenario with a slow correct process)

In the scenario "p_j faulty, p_{d+2} correct but slow", validity gives the hull of X_i^j ∪ {x_{d+2}}, not H(X_i^j), and with the paper's fixed choice x_{d+2} = 0 and j = d+1 the argument gives no contradiction.

Impact. Statement true (theorem_4); only the choice of x_{d+2} changes.

Details

The paper's own remark that "p_i has no information about x_{d+2}" already implies the fix: choose x_{d+2} per scenario inside H(X_i^j). Only the later sentence fixing x_{d+2} = 0 for all scenarios is inconsistent with that remark.

Repair

We pick the slow group's input per scenario (theorem_4).

The formalizationmodel, Lean names of the results, trust

Model.

  • Exact BVC and the lower bounds use CSLib's Byzantine message-passing model Cslib.Byzantine.PartialSync. It has a complete network of n = |P| deterministic state machines and at most t Byzantine processes. The adversary chooses the faulty set, the inputs, the Byzantine messages (which may differ per receiver) and the delivery times. Synchronous runs are runs with gst = 0; the bounded delay δ is arbitrary.

  • "Asynchronous" lower bounds are proved in the partially synchronous model (any finite gst). It has fewer runs than the asynchronous model, and its processes have synchronized clocks, so the impossibility is stronger than the paper's.

  • Specifications. Exact BVC uses CSLib's SolvesConsensusSync with bvcValidity (decision in the convex hull of the correct inputs). Approximate BVC is SolvesApproxBVC/SolvesApproxBVCSync: termination, ε-agreement in every coordinate, and validity, for correct inputs in a domain K.

  • Theorem 5's algorithm is modelled on the level of round exchanges (RoundExec), exactly as the paper's proof uses them. In each round, every correct process obtains a set B_i of senders and tuple values. Byzantine values may differ per receiver. Correct senders carry their current state (Property 3), and at most one tuple per sender is built in (Property 2). Properties 1 and |B_i| ≥ n − f are hypotheses (RoundExec.Valid). AAD's Component #1 itself (reliable broadcast + witnesses, from [AAD04]) is not implemented: Theorem 5 is proved for every execution in which Component #1 delivers sets with Properties 1–3, as in the paper.

  • The Section 4 synchronous structure is modelled directly (RestrictedAlg, SyncExec): the state is a vector, the update is arbitrary and may depend on the round number, and Byzantine processes send arbitrary vectors to each receiver.

Main.lean

Theorems 1 and 4 need n ≥ 2 and d ≥ 1, as the paper assumes in its introduction (n > 1, d > 0): with one process BVC is trivially solvable for every f (ownInput_solves_of_card_one).

The paper's claim that n ≤ d+1 (resp. n ≤ d+2) processes do not suffice, called "easy to see", needs a different argument for n = 2, and the simulation step for f > 1 ("f simulated processes per process") is only sketched. We use a direct partition of the processes into d+1 (resp. d+2) groups of size ≤ f, which covers all cases. The 3f+1 part of Theorem 1 cites scalar consensus. The reduction (diagonal inputs) is correct. The classical bound needs n ≥ 3, and n = 2 follows from the (d+1)f+1 part.
