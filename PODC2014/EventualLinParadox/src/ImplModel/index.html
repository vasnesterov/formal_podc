import Papers.PODC2014.EventualLinParadox.Basic /-! # Implementations, executions and progress conditions (Section 3) An implementation (`Impl`) of a high-level object gives every process a deterministic program: `invoke` (the local state after an invocation) and `act` (what a process with a pending operation does next: access a base object `x` with operation `o` and continue with `k r`, take a local step, or return a response). Processes may be infinite-state (the paper's programmes are Turing machines; we do not require computability). Two semantics: * **Eventually linearizable base objects** (`elSys`, Theorems 12, Proposition 14, Proposition 16). A base access is split into an invocation step and a later response step of the same process (the base objects are wait-free: a process with a pending base operation can always take its response step). The adversary chooses the responses; an execution is *admissible* (`ELAdm`) iff the history of every base object `x` is eventually linearizable with respect to `x`'s type. * **Atomic (linearizable) base objects** (`atSys`, Proposition 18). A base access is one atomic step that applies a transition `δ (mem x) o r q'` of the base object's (possibly nondeterministic) type; the label records the chosen `(r, q')`. Both are instances of a deterministic labelled system (`LSys`): an execution is a sequence of labels `lab : ℕ → Option Lab` (`none` = no step at that time), all enabled (`Proper`). Step `n` writes its high-level event (if any) at position `n` of the history `hist`, so operations are named by the step of their invocation. Executions are infinite sequences; a finite execution is one that is eventually `none` (a process may stop taking steps at any time, i.e. crash). Progress conditions (`WaitFree`, `ObstructionFree`, `NonBlocking`) and correctness conditions (`IsLinearizable`, `IsEventuallyLinearizable`) quantify over admissible executions. -/ namespace
