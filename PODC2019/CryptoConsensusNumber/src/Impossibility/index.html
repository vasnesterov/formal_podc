import Papers.PODC2019.CryptoConsensusNumber.System /-! # `k`-shared asset transfer cannot solve consensus for more than `k` processes The "at most `k`" half of Theorem 2 (and Corollary 1 for `k = 1`). The paper derives it from Lemma 2 (a wait-free implementation of `k`-shared asset transfer from registers, an atomic snapshot and `k`-consensus objects), the cited fact that `k`-consensus objects cannot solve `(k+1)`-process consensus, and (implicitly) composition of linearizable implementations. We give a direct valency proof instead. Proof. Take a critical configuration (CSLib: `biv_initial`, `exists_crit`); all processes are poised on the same object (`Crit.poised`), and some process `p` is on team `0`, some `q` on team `1`. * A read/write object is impossible (`Crit.not_forall_poised_of_rwLike`: a read or failing operation followed by anything, or two blind writes). * On an asset-transfer object: if `p`'s operation is a read or a failing transfer it does not change the state (`Team.false_of_absorb`); likewise for `q`. So both are successful transfers, by their callers (`Honest`), hence `p` and `q` own the source accounts. If the source accounts differ, the two transfers commute (`Team.false_of_commute`). So **every** pair of processes on opposite teams withdraws from one common account `a`, and then every process (being on some team) owns `a`: `|μ(a)| ≥ n > k`. -/ namespace CryptoCons open
