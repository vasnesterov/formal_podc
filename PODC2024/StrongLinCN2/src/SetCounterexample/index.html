import Mathlib.Tactic.FinCases import Cslib.Computability.Distributed.SharedMemory.Objects.FetchAdd import Cslib.Computability.Distributed.SharedMemory.Objects.Iface import Cslib.Computability.Distributed.SharedMemory.Objects.TestAndSet import Cslib.Computability.Distributed.SharedMemory.StrongLin /-! # Algorithm 2 (a set from test&set) is not strongly linearizable Attiya, Castañeda and Enea, *Strong Linearizability using Primitives with Consensus Number 2* (PODC 2024), Section 4.3, Algorithm 2: a set (`Put(x)` / `Take()`, where `Take` removes and returns an arbitrary element, or `EMPTY`) implemented from an infinite array `Items` of read/write registers (initially `⊥`), an infinite array `TS` of test&set objects (initially `0`) and a readable fetch&increment `Max` (initially `1`): ``` Put(x): max = Max.fetch&increment(); Items[max].write(x); return OK Take(): taken_old = 0; max_old = 0 while true: taken_new = 0 max_new = Max.read() - 1 for c in 1..max_new: x = Items[c].read() if x ≠ ⊥ then if TS[c].test&set() == 0 then return x if taken_new == taken_old ∧ max_new == max_old then return EMPTY taken_old = taken_new; max_old = max_new ``` The pseudocode never increments `taken_new`; the (probably intended) reading where `taken_new` is incremented whenever `TS[c].test&set()` returns `1` is modelled too: the parameter `countTaken : Bool` of `alg2` selects the reading. The counterexample works for both. ## The counterexample Three processes: `0` does `put 1`, `1` does `put 2`, `2` does `take`. In the prefix `pre`, both puts perform their fetch&increment (`Max = 3`), the take performs a full first scan (both items `⊥`; `max` changed from `0` to `2`, so it scans again), reads `Max` again and reads `Items[1] = ⊥`; then `put 1` writes `Items[1]` and **completes**. * Extension `exB`: the take reads `Items[2] = ⊥`, the double-collect test succeeds and it returns `EMPTY`. Since `put 1` completed before, the take must be linearized *before* `put 1`, hence already in the linearization of `pre`, with response `EMPTY`. * Extension `exA`: `put 2` writes `Items[2]`, the take reads it, wins `TS[2]` and returns `2`. The linearization of `pre` (a prefix of that of `exA`) already contains the take with response `EMPTY`, a contradiction. Hence no prefix-closed linearization function exists (`alg2_not_stronglyLinearizable`). (We do not prove anything about plain linearizability of Algorithm 2.) ## Modelling * The implemented set is the nondeterministic sequential specification `setSpec` (`NSpec`, states `Set ℕ`, `take` returns any element, or `empty` on the empty set). The `ObjSpec` `setOps` is only used for its operation/response types: it is the interface-only object `ObjSpec.iface SetOp SetResp`, whose transition function is a dummy and is **never used** (`NStronglyLinearizable` only refers to `setSpec`). * Items are natural numbers; `⊥` is `none`.
