Is a LOCAL Algorithm Computable? — PODC 2026

Antonio Cruciani, Avinandan Das, Massimo Equi, Henrik Lievonen, Diep Luong-Le, Augusto Modanese, Jukka Suomela. Brief Announcement: Is a LOCAL Algorithm Computable? PODC 2026. DOI 10.1145/3796701.3815908. Formalized version: the full version, arXiv 2602.21022 v2; numbering follows it. Copy of the paper: paper.pdf.

DOI · arXiv · PDF · All differences · Lean source · GitHub

Verdict: 🛠️ Hard fix. The paper's main result, the separation Theorem 4.1 (an LCL Π with complexity O(log n) in uncomputable-LOCAL but Ω(√n) in computable-LOCAL, i.e. classes I < II of Table 1), was not checked: the LCL Π of Section 4 is not formalized, only the diagonalization core of Lemma 4.17 (on abstract hypotheses) and Lemma 4.18. The equivalences of Section 5 hold, in slightly greater generality: with a bound n ≤ N (or n ≤ N ≤ f(n)) uncomputable and computable LOCAL coincide (Theorem 5.3), in uncomputable LOCAL the bound does not help (Theorem 5.4 / Corollary 5.6), and critical views are decidable (Lemma 5.2). Saving them took a redesign of the paper's central tool, "maximally T-safe neighbourhoods", as "critical" views.

Mistakes in the paper

✏️ Slips

  • Definition 5.1: "maximal" vs. "safe with t+1 unsafe" coincide only if safety is downward closed, which is not shown, so "the" maximally safe neighbourhood of a node need not be unique. Our first critical radius settles it, and no theorem depends on the difference.

  • Lemma 5.2, step 3 ("reject if ... t < T(n)") has the inequality reversed: it should be T(n) < t.

  • Theorem 5.3's proof does not say which class "safe" ranges over. If safety ranges over all graphs, the final contradiction uses a network that need not satisfy the promise n ≤ N ≤ f(n) for the same N, and the uncomputable algorithm owes nothing there. Definition 5.1 has a class parameter 𝒢, and with the promise class the contradiction works. We prove the theorem by a different argument: for fixed N, search over the finitely many finite tables "(view, radius) ↦ output" for one that solves the problem on all legal networks. The uncomputable algorithm's table shows that the search terminates (exists_computable_of_promise).

  • In Lemma 4.17, "do not see farther than the first k−1 layers" must also avoid the constantly many special layers near the bottom.

  • In Lemma 4.17, "the value computed by T will equal k₀" is not true in general, but any k with the property works (Model.exists_far_of_computable).

Proof gaps in true statements (5)Definition 5.1 · Lemma 5.2 · Lemma 5.2 · Lemma 5.5 · Definition 3.5

🛠️ Definition 5.1 ("maximally T-safe"; used in Lemma 5.2 and Theorems 5.3–5.4)

Maximal safety of radius t depends on the unseen radius-(t+1) view, so the paper's algorithms that "grow the view until it is maximally T-safe", read literally, exceed the time bound by one round: in C₃ with T(n) = ⌊(n-1)/2⌋ they cannot stop within T(3) = 1 (maxSafe_rule_exceeds).

Impact. Theorems 5.3 and 5.4 are true and proved with a corrected notion ("critical" views). Under the view-level reading the algorithms stay within T(n), but then the paper's proofs of Lemma 5.2 and Lemma 5.5 do not handle that notion.

Details

t is maximally safe for v if t is safe and t+1 is not, and safety of t+1 is defined with radius-(t+1) neighbourhoods. A node that has seen only N^t(v) cannot evaluate this. Yet both algorithms "grow the view until it is maximally T-safe" and are claimed to run within T(n) rounds.

Counterexample with T(n) = ⌊(n-1)/2⌋: a node of the triangle and a node of the 5-cycle have the same radius-1 view (same identifiers and ports). Radius 1 = T(3) is maximally safe in C₃, since radius 2 is unsafe because of C₃ itself. In C₅ it is not maximally safe: every network containing the radius-2 view has ≥ 5 nodes, so radius 2 is still safe. So no ball-growing rule stops exactly at maximally safe radii. Any algorithm that never stops before a maximally safe radius fails to stop within T(3) = 1 rounds in C₃ (maxSafe_not_view_determined, no_alg_stops_at_maxSafe, maxSafe_rule_exceeds); the view-level reading is sound (maxSafeView_iff, first_critical_maxSafeView).

The paper's sentence "if t is maximally safe for v, then N^t(v) is maximally safe" can also be read as a property of views: maximally safe for some node with this view. Under that reading the radius-1 view above is maximally safe, also in C₅, and the algorithms stay within T(n). A view is then maximally safe iff it is safe and critical (below). The first such radius of a node is exactly its first critical radius, which is where our B stops. But then the paper's arguments do not establish what is needed: Lemma 5.2's procedure tests only safety of t, never criticality, and Lemma 5.5 does not show that A_N stops within the view. So in either reading the statements are true and the gap is in the proofs.

Repair

Call a radius-t view critical if it occurs in some network G' with T(|V(G')|) ≤ t. Every node meets a critical radius by T(n), and any algorithm of locality T has already stopped there (Model.Critical, out_of_critical). Maximal safety implies criticality (MaxSafe.critical). Section 5 is reworked on this notion (Model.exists_boundFree, Model.sandwich_computable).

🔧 Lemma 5.2 (the procedure tests only safety)

The procedure tests only safety of t and never that t + 1 is unsafe, so it does not decide maximal safety in either reading of Definition 5.1.

Impact. Decidability holds for critical views (Model.critical_decidable).

Repair

Add the bounded search for a witness network with T(n) ≤ t.

🔧 Lemma 5.2 (case split)

The case "t = T(N') = C" misses t > sup T.

Impact. The decidability claim stands (Model.critical_decidable).

Repair

The case should read "T bounded with supremum C ≤ t", and step 1 should accept for t ≥ C.

🔧 Lemma 5.5 (inside Theorem 5.4)

The proof takes the neighbourhood X_i itself as a graph, which is not a network, and then only gets that A_N stops within T(N_i) rounds, while the sandbox needs A_N to stop within the radius of X_i.

Impact. Statement true; the rest of the proof of Theorem 5.4 stays (exists_boundFree).

Details

X_i is not a network: boundary degree labels count unseen edges.

Repair

Take N_i to be the size of a criticality witness (exists_boundFree).

🔧 Definition 3.5 (why the locality T is non-decreasing)

The paper's reason, "the set of graphs with n₁ nodes is contained in the class of graphs with n₂ nodes", is false.

Impact. The claim is true, for a different reason (stops_of_le).

Repair

Pad with isolated nodes that have fresh identifiers (identifiers lie in [1, n^c], c ≥ 1); this does not change the views (stops_of_le).

The formalizationmodel, Lean names of the results, trust

Model.

  • Deterministic synchronous LOCAL, ball-growing formalism (Definition 3.5). An algorithm is A : View → ℕ → Option Out (none = ⊥). A node outputs A (view, t) at the least radius t with a non-⊥ value. Locality T means every node of every n-node network stops by radius T(n).

  • Abstract networks (Model Net View). Networks have sizes, and views of every node and radius. The radius-t view determines all smaller ones; this is the only property used.

  • Concrete instance (concreteModel Δ c k): the networks of Section 3. Simple graphs of maximum degree Δ, port numbering = neighbour order, unique identifiers in [1, n^c], inputs < k, full-information views (own identifier, input, degree, and the neighbours' radius-(t−1) views in port order). With unique identifiers these carry the information of N^t(v) (Definition 3.1) except the port numbers, at the distance-t nodes, of their edges towards distance-(t−1) nodes. So the concrete model sees slightly less than Definition 3.1 (as if messages were not tagged with the sender's port). The abstract theorems apply to either kind of view. The C₃/C₅ counterexample also holds for Definition 3.1 views: the ports match.

  • Knowledge of n: a common input N with promise n ≤ N (UpperBound) or n ≤ N ≤ f(n) (Sandwich f). An algorithm is then a family A N.

  • Problems are arbitrary validity predicates on output labellings (LCLs and beyond). Theorem 5.4 uses a finite output alphabet. Theorem 5.3 uses a computable validity check.

  • Computability is Mathlib's Computable on Primcodable encodings of (N, view, radius). Uncomputable-LOCAL algorithms are arbitrary functions.

Not formalized. The LCL Π of Section 4 (trees, rows, growing grids, Turing machine and consensus layers; Lemmas 4.4–4.16, Corollary 4.14). Hence Theorem 4.1 and the strictness I < II are not verified. Only the diagonalization of Lemma 4.17 is formalized, for an abstract family G_K(x) whose two properties (validity forces the halting result; the node holding x does not see the bottom) are hypotheses; whether Π really forms such a family is open. The equivalence of full-information views and Definition 3.1 balls and the direct computable O(log n) algorithm with a bound N (end of Section 2.1) are not formalized.

Trust. No sorry; the listed theorems use only the axioms propext, Classical.choice, Quot.sound. Non-vacuity checks:

  • every node has a critical radius (critical_self);

  • the concrete model satisfies the abstract hypotheses: restriction in Concrete.lean; computability in ConcreteComputable.lean: primitive recursive well-formedness, enumeration of networks with ≤ N nodes, computable injectively coded views;

  • a toy separation family on promised paths (SeparationToy.lean): uncomputable locality 0 (toy_uncomputable_solves) versus computable locality ≥ n − 1 (toy_computable_lower).

Computable list combinators (Computable.list_foldl/map/all/any/findSome?/filterMap/flatMap/filter, Computable.nat_find) and Primrec.list_all/any, Primrec.nat_pow are shared code in CSLib Cslib/Computability/Partrec/List.lean and Cslib/Computability/Primrec/List.lean.
