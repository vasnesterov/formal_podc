Consistent Refereeing: Impossibilities for Strong Linearizability — PODC 2026

Verdict: 🛠️ Hard fix. All theorems we formalized hold: Theorems 1, 3, 4, 5, 25, 30, Proposition 11, Corollary 12, and Lemma 14 for counters, max registers and snapshots. The proof of Theorem 30 fails in its test&set case, and closing it took a new argument. The other mistakes are one local repair in Lemma 17 and slips.

Mistakes in the paper

✏️ Slips

  • Lemma 29(2) fails in the degenerate case w = 0: the sequences it needs (|γ| = w, γ = qλ) do not exist. We use window max(w, 1) (a 0-window object is also 1-window-like), and our proof of Theorem 30 does not need Lemma 29(2) at all.

  • Lemma 17 needs decide to be pending. This implied assumption holds where the lemma is used, and the lemma is proved with it (lemma17).

  • The last paragraph of Theorem 25 ("We have that αβp is closed. Otherwise…") is garbled; we formalized the intended argument (theorem25).

  • Lemma 28's test&set case calls αβq′ closed, but it is supervalent there; the case needs only αβq closed (lemma28).

Typos

  • Lemma 29's proof cites Lemma 21 instead of Lemma 27.

Proof gaps in true statements (2)Theorem 30, case "all processes apply T&S to the same test&set object R" · Lemma 17

🛠️ Theorem 30, case "all processes apply T&S to the same test&set object R"

The proof claims that αβγpγ′₁q′ᵏγ′₂ and αβγ′₁q′ᵏγpγ′₂ end with the same shared memory and look the same to every other competitor q″, but if R is still unset after αβ, q wins the test&set in the first execution and q′ in the second.

Impact. Statement true; closed with a different argument (const_valency_contra, theorem30).

Details

  • q′ then takes k more steps in different local states, and so do the processes of γ′₂. These steps may write different values to other objects, and q″ can read them.

  • So neither the memory equality nor the indistinguishability follows.

Repair

Our fix does not use Lemma 29(2). Once some competitor has set R, every later referee step on R changes nothing and commutes with every competitor step. By Lemma 17 the singleton valency W(αβq·u·p) is then the same for every competitors-only extension u. Taking u in which some competitor completes more operations than that value contradicts the specification. (const_valency_contra, theorem30)

🔧 Lemma 17 (counting q's operations)

q's operations are counted in αβ′ and then transferred to α′β′σ, but α′ may contain a different number of operations of q, since indistinguishability compares only states.

Impact. Statement true (lemma17).

Repair

Count the operations inside β′, which wait-freedom gives just the same.

The formalizationmodel, Lean names of the results, trust

Model.

  • CSLib's asynchronous shared-memory model (Cslib.SharedMemory.Impl).

    • Deterministic processes; atomic base objects with deterministic sequential specifications.

    • Executions are label lists, and responses are separate steps.

    • Crashes are processes that stop taking steps.

  • P is any finite type of processes with a referee ref; all other processes are competitors.

  • compete carries the caller's id, because objects cannot see the caller. The implementation must allow each role's operation.

  • The contest object of Section 4 is one-shot by definition, but our model lets a process invoke operations repeatedly. Statements that hold only for one-shot use are therefore restricted, and this is not an error in the paper:

    • Proposition 11 and Theorem 3 are proved on executions where the referee decides at most once. Theorem 3's algorithm is not linearizable with two decides. Proposition 11 also assumes an injective encoding of process ids as queue values.

    • Theorem 4: the paper's algorithm would overflow the (n−1)-window under repeated competes. Our variant writes only on the first compete, so it is the same algorithm on one-shot executions, and it is strongly linearizable on all executions.

    • Theorem 5 says "wait-free" and the introduction says "lock-free". On one-shot executions the two coincide: there are only finitely many operations, so both say that no such execution has infinitely many steps. We prove both (theorem5_lockFree, theorem5_waitFree).

  • Correctness and progress are assumed only on admissible executions, which makes the impossibility results stronger. Corollaries give the versions with the unrestricted LockFree/WaitFree/ StronglyLinearizable.

    • One-shot contest (Adm): every process invokes at most one operation, the one of its role, and the referee starts after some compete completed.

    • Long-lived contest (LLAdm): roles are respected and the referee decides at most once.

  • The long-lived contest is a nondeterministic specification (llSpec): decide may return any bound on all competitors' counts. Strong linearizability is taken with respect to it.

  • Base objects are given by semantic classes (Cslib/Computability/Distributed/SharedMemory/ObjClasses.lean, Cslib/Computability/Distributed/SharedMemory/ObjClasses/Basic.lean):

    • Herlihy-interfering (per state);

    • window-like with window w (w-window registers are window-like with every w′ ≥ w);

    • stack-like (isomorphic to a stack);

    • read/write (every primitive is read-only or a blind write);

    • test&set-like (every primitive sets the object to a fixed state).

Proof remarks. The case analyses of Lemmas 20, 23, 27, 28 and Theorems 25, 30 omit the referee's invocation and response steps; these are routine completions in the formalization.

Not formalized.

  • Decisive linearizability, so Theorems 3 and 13 are not covered as decisive. Theorem 13 is not formalized at all; Theorem 3 is proved only as linearizable.

  • Lemma 14 for fetch&increment and fetch&add, and from strongly linearizable implementations.

  • The paper's own proof of Theorem 1, which we obtain through Corollary 12.

  • Theorem 5, stack case 4c (one push, one pop), as the paper argues it. It refers to case 4b, "conceiving the step of p_i as a push of u_i", but the two orders leave different stack shapes than in 4b (u_j·T vs s₀·T, where s₀·T is the stack in C), so the transfer is not immediate; we did not decide whether the case holds up as written. Theorem 5 itself is proved by a replacement argument covering 4b and 4c (Crit.stack_push, lockstep):

    • Run the canonical extension (a third competitor solo, then the referee) from α·i·j and from α·j in lock-step. The stacks are X₁ ++ S and X₂ ++ S and differ only below a common top.

    • If no step pops into X₁/X₂, the referee returns the same value from a descendant of α·i and of α·j.

    • Otherwise, at the first such pop by q, the configurations α·i·j·β·q and α·j·β·q·i are identical.

    • The "w.l.o.g. pushed values are distinct" step (footnote 3, stamping) is standard and sound, but our proof does not need it.

  • Corollaries 26 and 31: they need a general composition theorem for strongly linearizable implementations. For queues (Proposition 11) the composition is done concretely.

Trust. No sorry; the listed theorems use only the axioms propext, Classical.choice, Quot.sound.

Non-vacuity.

  • theorem4 gives an implementation meeting every hypothesis of Theorem 5 except the window bound, and the (n−1)-window register is not (n−2)-window-like, so Theorem 5 is tight.

  • lemma14_* give wait-free strongly linearizable long-lived contest implementations, so the hypotheses of Theorems 25/30 are not contradictory on their own.

  • register_rw, windowObj_hyp30, tasObj_hyp30, register_interfering, stackObj_stackLike: the standard objects belong to the classes.

  • StrongLin/Restricted.lean, Progress.lean: strong linearizability and progress (LockFreeOn, WaitFreeOn, ObstructionFreeOn) restricted to a set of executions; Solo.lean: finishing pending operations by solo runs (Impl.exists_finish).

  • Objects/ (window registers, stacks, queues, counters, max registers, snapshots; ObjSpec.iface for the long-lived contest's interface llObj) and ObjClasses.lean (object classes).

  • LinResp.lean (ObjSpec.respIn: responses in sequential histories), History.lean (curOp, linState_concat, prefix lemmas), Run.lean (forward step equations, run_induction), Covering.lean (agreement of configurations, poised processes and block writes Impl.runFrom_poised_block, and the locality/commutation lemmas Impl.step_exact, Impl.step_comm), StrongLin/OneAccess.lean (single-access implementations, Theorem 4 and Lemma 14).
