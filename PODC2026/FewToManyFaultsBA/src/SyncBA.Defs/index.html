import Mathlib import Cslib.Computability.Distributed.Byzantine.LockStep.Sequential /-! # The synchronous protocol `SyncBA` (Appendix B.1–B.3): definitions Formalization of the synchronous Byzantine agreement protocol `SyncBA` of A. Constantinescu, M. Dufay, A. Paramonov, R. Wattenhofer, *From Few to Many Faults: Optimal Adaptive Byzantine Agreement* (PODC 2026, arXiv 2505.19989), behind Theorem 3.1: `ViewByzantineAgreement` (Appendix B.1) with the synchronous retrieval protocol (`RetrievalLeaderSync` / `RetrievalPartySync`, Section 10.1), run for `n` views, followed by the fallback detection of `SyncBA` (Appendix B.3) and a black-box quadratic fallback protocol. ## Model CSLib's synchronous lock-step model `Cslib.Byzantine.LockStep` on the complete network of the parties `Fin n` (one round = `Δ`), static Byzantine set, ideal signatures (`Cslib.Byzantine.LockStep.Auth`). Threshold signatures are modelled as *sets of partial signatures*: a token `(q, s) : Tok n` is `q`'s partial signature on the statement `s`, and a `k`-certificate on `s` is a set of at least `k` tokens on `s` (`Valid`); since tokens are pairs, the signers are distinct. (A real threshold signature is one word; we count messages, not bits.) ## The protocol View `v < n` occupies rounds `11v, …, 11v+10` and has leader `v mod n` (round robin, so every party leads exactly one view). Phases (`j = r mod 11`; `P` = party role, `L` = leader role; a message from `p` to `q` carries the party-role component for `q` = leader and the leader-role component for `p` = leader; the leader receives its own messages through *self-delivery*): * `j = 0`: P sends `Complain` if it has no commit; L (without commit) sends `ReqSuggestion`. * `j = 1`: P answers `ReqSuggestion` with its commit, else its key, else nothing; it is *active* in the view iff it has no commit. L with a commit (from before the view) answers complaints. * `j = 2`: L (running the leader protocol) broadcasts a commit if it knows one; otherwise it proposes the highest key suggested (in phase 4); otherwise it broadcasts `RunRetrieval`. * `j = 3`: active P answers `RunRetrieval` with a partial signature on its retrieval input (both values if the input was set to `⊥`). L combines a `(t+1)`-certificate for a value, or sets its own retrieval input to `⊥` and stays silent (`RetrievalLeaderSync`). * `j = 4, 6, 8`: L sends `ProposeKey` / `ProposeLock` / `ProposeCommit`; `j = 5, 7, 9`: active P checks and answers with a partial signature (`CheckedKey`, …), updating its key (on `ProposeLock`) and lock (on `ProposeCommit`); the key phase checks the lock. * `j = 10`: L broadcasts the commit (`SendCommit`). * any round: a valid `SendCommit` sets the commit, which is the decision. Then (rounds `11n`, `11n+1`, `11n+2`): `HELP` if no commit; `PROOF` replies and `FALLBACK` certificates (`t+1` help signatures); `LOCK` broadcast by parties with a fallback certificate. At round `R₀ = 11n+3` stage A ends with the record `Rec` (participate in the fallback?, value). Stage B runs a black-box BA protocol `Afb` among the participants (others are silent); a party without commit decides its output (or its value if it does not participate). -/ namespace
