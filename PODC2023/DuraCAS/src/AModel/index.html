import Papers.PODC2023.DuraCAS.Spec /-! # DuraCAS over atomic durable EC objects (the A-level model) Appendix A.3 of the full version starts with: "Lines 21 to 24 of `RECOVER()` ensure that `W.RECOVER()` or `Z.RECOVER()` is executed before any other operation is executed on `W` or `Z`. Consequently, the durable objects `W` and `Z` behave like atomic EC objects." This file makes the right-hand side precise, and `Refinement.lean` proves the claim (for the per-process discipline). An *atomic durable* EC object behaves as follows: * `ECLL` and `ECSC` are atomic steps; `ECSC(h, s, v)` succeeds iff `seq = s`, and then sets the object to `(ŝ, v)` with `ŝ = max(DETECT(h), s) + 1` and `DETECT(h) := ŝ` (this is exactly the sequence number DurEC chooses; the abstract `DETECT` value of a handle is `ls h`); * a call returns in a separate step (`APc.aft`), so the effect of an `ECSC` may precede its return; * if a process crashes while poised at an `ECSC`, that `ECSC` may stay pending as an *orphan* (`Orph`) that may take effect later (`Lbl.orph`) or be dropped (`Lbl.drop`); `RECOVER` of the object (lines 22–25) can complete only after the orphan on that object is resolved. The DuraCAS code is the same as in `Model.lean`; `ECLL` and line-21 steps are as there. -/ namespace Podc.DuraCAS variable {P K V : Type} [DecidableEq P] [DecidableEq K] [DecidableEq V] variable (P K
