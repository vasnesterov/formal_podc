Bounded Timestamping from Standard Primitives — PODC 2023

Benyamin Bashari, Ali Jamadi, Philipp Woelfel. Efficient Bounded Timestamping from Standard Synchronization Primitives. PODC 2023. DOI 10.1145/3583668.3594601. Formalized version: the 45-page full version with appendices (University of Calgary report). There is no arXiv version. Numbering follows the full version. Copy of the paper: paper.pdf.

Verdict: ❌ Intent lost. The algorithm of Figures 1–2 is not linearizable: Lean checks a sequential execution with 3 processes in which isEarlier(1, 0) gives the wrong answer, so Lemmas 6, 8 and 9 and Corollary 10 are false and Theorem 1 is not established by it. A simple repair (a separate link for helpMoveTS) blocks our attack, but we did not prove it correct, so the paper's main point is not saved. What stands is Section 6 (bounded FAI from bounded FAA), with a slightly better bound, and the constant step complexity (Lemma 12): every operation takes at most 2κ + 107 base-object steps, independently of n.

Mistakes in the paper

❌ Theorem 1 and Corollary 10 via Lemma 6 (linearizability of Figures 1–2)

The algorithm is not linearizable, because the helpMoveTS() coroutine shares its LL/SC links with the process's other LL()s: with n = 3, κ = 4 a sequential execution makes isEarlier(1, 0) return false (alg_not_linearizable), and Lemma 6 is false (lemma6_false).

Impact. Lemmas 6, 9 and 8 and Corollary 10 are false for Figures 1–2, and Theorem 1 is not established. A simple repair (a separate link for helpMoveTS) blocks our attack, but we did not prove it correct. Section 6 and the constant step complexity (Lemma 12) are unaffected.

Details

  • The cause is reusable: a helpMoveTS() call spread over several operations shares its LL/SC links with the rest of the process's code.

  • Line 23 executes helpMoveTS() κ steps per helpActiveCluster() call, so one call is spread over several operations of the same process.

  • Those operations perform their own LL()s on TS entries: isEarlier lines 35/37/44/45/50, helpUpdateTS line 9, conditionalReset line 29.

  • With one link per process and object, which is the paper's LL/SC definition in Section 3, such an LL() renews the link that the coroutine later checks with VL() (line 65) and uses for SC() (line 73).

  • Lemmas 46 and 51 still hold in our execution; only their use in the proof of Lemma 6 breaks. Lemma 6 itself fails: an SC() of line 73 changes TS[0] from (1, 63) to (1, −1) while TS[1] = (1, 61), which reverses their dominance order (lemma6_false). Lemma 9 then fails as well.

Counterexample (n = 3, κ = 4; every operation runs solo):

  1. Process 0 calls updateTS() 371 times and process 1 calls it 62 times. Cluster 1 is now in its move phase and TS[2] has been moved.

  2. Process 2 calls isEarlier(0,1). Its coroutine reads TS[0] = (0, 370) (line 61) and pauses.

  3. Process 0 calls updateTS() twice. Now TS[0] = (1, 63), and the flag has its old value again.

  4. Process 2 calls isEarlier(0,2). Line 35 renews its link on TS[0]. Its coroutine's VL() succeeds, and line 73 writes (1, −1) into TS[0].

  5. isEarlier(1,0) returns false. The specification says true.

The execution has 438 operations and 6392 steps. Python experiments give analogous violations for n = 4, 5, 6 with κ = 3 (the smallest admissible κ) and for other readings of lines 70–72. (alg_not_linearizable)

❌ Observation 13, Lemma 14 and Lemma 2 (at most 6 Counter increments)

An updateTS() can increment Counter up to 12 times before its first helpActiveCluster() call, not at most 6, because helpSystem() may call isEarlier() (line 18), which runs two helpUpdateTS() calls first (observation13_false: 7 increments in one updateTS(), no helpActiveCluster() started).

Impact. Lemmas 21 and 33 lose their proofs, because their constants ζ = 6n + 2 and μ = 6n³ + 6n² + 2 rely on the bound 6. Larger constants probably repair this; we did not check.

Details

The count of 12 is informal; Lean shows 7. The Lean witness calls isEarlier(2, 2). The oversight does not depend on x = y, since the two helpUpdateTS() calls exist for any arguments, but a witness with x ≠ y is not in Lean.

✏️ Slips

  • Observation 56: isEarlier(x, x) can return true. For x = y, lines 44–46 validate only the second LL(), so if process x completes an update between lines 44 and 45 the comparison sees two different values of TS[x] (alg_not_linearizable_self). Observation 56 tacitly assumes x ≠ y, and returning false for x = y fixes it.

  • Proof of Lemma 8, Case 2b: the text says "i ≺ j at point t*x1" where t*y1 is meant.

  • The informal specification in Section 1 disagrees with the interpreted value of Section 5. In Section 1, isEarlier(p, q) is false when only p updated. In ≪ and the interpreted value it is true. We formalize the latter.

  • Section 6: T = n(m − 1) should be n(φ − 1), as in Figure 3.

  • Section 3 promises a mod φ-FAI for any φ ∈ {0, …, ⌊2^w/n⌋}, but φ = 0 is meaningless and the top value φn = 2^w is outside Theorem 11's hypothesis B > φn; the sharper bound B ≥ φn covers it.

Typos

  • "mod 3δ-FNI" should be "FAI".

  • Lines 70–72 do not say what to do with ⊥ indices; the prose ("dominant", "dominated active timestamp") settles it.

  • Process n − 1 may not call updateTS(), so "n-process MTS" really means n − 1 updaters. The paper says so, and running one more process gives n.

The formalizationmodel, Lean names of the results, trust

Model.

  • Asynchronous shared memory, using CSLib Cslib.SharedMemory.Impl.

    • n deterministic processes.

    • Each base-object primitive is one atomic step.

    • Wait-freedom is CSLib's WaitFree. Linearizability is CSLib's Linearizable, which is Herlihy–Wing.

  • The implemented object is mtsObj n. Its state is the order of the processes' latest updateTS(), followed by the processes that never updated, by identifier. It is the paper's "interpreted value".

    • updateTS() of p is the operation upd p, and only p may invoke it.

    • Process n − 1 never updates.

  • Base objects (Corollary 10 level), from Defs.lean:

    • bits A[i];

    • LL/SC objects TS[i] and LookupTable[i], with one link per process as defined in Section 3;

    • one atomic mod 3δ FAI object Counter, with the paper's constants ζ, η, μ, γ, δ.

  • alg n κ (Alg.lean) encodes Figures 1–2 line by line.

    • helpMoveTS is a persistent coroutine advanced κ steps per helpActiveCluster().

    • Lines 70–72 select the ≪-dominant / ≪-minimal entries.

  • Section 6 is modelled separately (BoundedFAI.lean). It uses a bounded FAA object whose overflow behaviour is an arbitrary function parameter.

Section 6 is correct. Lemma 63, Corollary 64 and Theorem 11 hold, for any overflow behaviour. The counter never exceeds φn − 1, so B ≥ φn suffices instead of B > φn. This is tight for φ ≥ 2.

Not formalized.

  • Proof of Lemma 8, Case 2b, second subcase: "i ≺ j at t*y2" needs t*x1 < t*y2, which the paper does not argue. We did not analyse this formally.

  • Lemmas 3–9 and 15–62 in general.

  • Linearizability of any repaired algorithm (a separate link context for helpMoveTS, and isEarlier(x, x) = false). In simulation the repair blocks our attacks. Random runs of the repaired algorithm found no violation, but random runs also miss the original bug, so this is weak evidence.

  • The O(log n) word-size bound (index range [−n, δ)).

  • The Jayanti–Petrovic LL/SC construction and the resulting O(n²) space.

  • Composing Section 6 into the algorithm.

  • Section 7.

Trust. No sorry. The listed theorems use only propext, Classical.choice and Quot.sound. decide +kernel adds no axiom. The model comes from CSLib's SharedMemory.{Model, History, LinPoints}. Python confirms the counterexample independently: our simulator and an offline linearizability checker agree with the Lean evaluation step for step.
