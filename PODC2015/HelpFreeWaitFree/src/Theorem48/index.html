import Papers.PODC2015.HelpFreeWaitFree.GVLoop /-! # Theorem 4.8: (strong) global view types have no wait-free help-free implementation The base objects are registers supporting `read`, `write` and `cas` (CSLib `casObject`). * `Ctx.iteration` — one iteration of the main loop of Figure 4.2. * `theorem_4_8` — **Theorem 4.8** for strong global view types (`StrongGlobalView`), for the weak (owner-only) notion of help-freedom: with three distinct processes, no wait-free implementation from read/write/cas registers has a weakly help-free linearization function. * `theorem_4_8_helpFree` — the paper's form: such an implementation is not help-free. ## Relation to the paper's proof The paper states Theorem 4.8 for all global view types (`GlobalView`: the results of a view tell how many of `op₁` and the next modifier `op₂` precede it). Its proof does not establish this: * **Claim 4.6.8 (gap, not repaired for `GlobalView`).** From "`op₁` is decided before `op₃` in `h∘p₁∘p₃` but not in `h∘p₃∘p₁`" the paper infers that `p₃` running solo returns different results for `op₃` ("because each operation by `p₁` changes the return value of `op₃`"). With only three result classes this does not follow: in both histories the result may lie in `RS1` — `op₁ ≺ op₃ ≺ op₂` in the first, `op₂ ≺ op₃ ≺ op₁` in some extension of the second. The same inference is used to exclude reads and failed `cas`, and the elimination of writes asserts without justification that `op₂` is not before `op₃` in the `p₁`-first run. We therefore assume `StrongGlobalView` (a view also tells *which* of `op₁`, `op₂` precedes it — the distinction the paper says it avoids using). Then whether `op₁` (or `op₂`) is decided before a view depends only on the memory and on `p₃` (`Ctx.kl`), and Claim 4.6.8 follows (`Ctx.caseA`; reads and failed `cas` are excluded by comparing `h∘p₁` with `h`, writes by help-freedom). * **Claim 4.6.12 (gap, repaired by changing the construction).** "`op_k` is not decided before `op_j` (because `op_j` may still be before `op₃`, which in turn may still be before `op_k`)" is unjustified: two different extensions do not give one with `op_j ≺ op₃ ≺ op_k`. When the step of `p_k` at line 25 would decide `op_k` before the next view, we show that the next steps of `p₁` and `p₂` are competing successful `cas` on one location (`Ctx.race`, `Ctx.bbad`) and perform the move of lines 17–20 instead (`Ctx.cas_move`); otherwise line 25 is harmless (`Ctx.good_move`). The final argument (Claim 4.6.15) is unchanged. Fetch&increment is a global view type (`fetchInc_globalView`) but not a strong one (`fetchInc_not_strongGlobalView`); the same holds for increment objects (views only count). For them Theorem 4.8 is not established here.
