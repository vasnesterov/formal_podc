Limitations of Highly-Available Eventually-Consistent Data Stores — PODC 2015

Hagit Attiya, Faith Ellen, Adam Morrison. Limitations of Highly-Available Eventually-Consistent Data Stores. PODC 2015. DOI 10.1145/2767386.2767419. Formalized version: the authors' copy of the PODC paper (10 pages). Lemmas 5 and 7 and parts of Theorem 12 are proved there only "in the full version" (IEEE TPDS 2017, not open access); we give our own proofs.

DOI · PDF · All differences · Lean source · GitHub

Verdict: ⚠️ Weakened. The paper proves two limitations, and one of them stands: the message-size bound of Theorem 12 holds (with ⌊n' lg k⌋ bits) by a new decoding argument. The OCC result, Theorem 6, is left unestablished by two broken proof steps that we could not repair, although it is not refuted. Lemmas 3, 5 and 7 and Corollary 4 hold (Lemma 5 needs two replicas), and Definition 14, which no store satisfies when read literally, is used with its evident intent.

Mistakes in the paper

❌ Theorem 6, Section 5.2.1 ("without loss of generality" revealing)

The proof assumes without loss of generality that the OCC abstract execution is revealing, but the extension by reads r_w need not be OCC (Gap.revealing_extension_not_OCC).

Impact. Theorem 6 (no eventually consistent store with invisible reads and op-driven messages satisfies a consistency model strictly stronger than OCC), and with it Lemma 11, is unestablished, not refuted: we have no store and OCC execution for which the construction of Section 5.2.2 actually fails. We state it (Theorem6Statement, for finite OCC abstract executions with distinct written values) without proof.

Details

Section 5.2.1 assumes the OCC abstract execution A to be realized is revealing: before each write w there is a read r_w of the same object with the same visibility as w. It justifies this by "adding the appropriate r_w operations and vis edges to A". But the inductive argument (Lemma 11) is then applied to every read of the extended execution, including the added r_w, and needs OCC for them. The extension need not be OCC. Take writes a at R₀ and b at R₁ to one MVR, concurrent, both visible to a write c at R₂, and no reads. This is OCC (vacuously). The added read r_c returns {a, b}, and there is no write to another object that could serve as an OCC witness. So the revealing extension is not OCC. (Gap.revealing_extension_not_OCC) This particular A is trivially realizable (no reads), and a cleverer extension (ordering a before b) is OCC. We do not know whether a suitable revealing OCC extension always exists.

❌ Theorem 6, proof of Lemma 11 (use of Lemma 7)

The proof of Lemma 11 uses Lemma 7 for w'_i →vis w_0, where w'_i is an OCC witness, a write to another object, which Lemma 7 does not cover.

Impact. This is the core step showing that the store cannot add "fake" visibility edges, so Lemma 11 and Theorem 6 stay unestablished, independently of the previous item. No repair is proved.

Details

Lemma 7 transfers visibility between writes of the operation context of a read, i.e. writes to the same object. "w'_i ∈ ctxt(A, e) since w'_i →vis w_0 →vis e" is wrong: contexts contain only writes to obj(e). For writes to different objects the conclusion of Lemma 7 fails in general: visibility between them is constrained by nothing that the reads r_w reveal, and eventual consistency only concerns writes to the same object. See differencies.md (item 15) for an example.

Repair

None proved. A repair would need revealing reads of every object before each write, which makes the previous gap worse.

✏️ Slips

  • Lemma 5, one replica. Lemma 5 is false with one replica: a single-replica store that never sends satisfies all assumptions, and after a write no message is pending (lemma5_false_one_replica). This degenerate case is the only numbered statement we refute; with two or more replicas the lemma holds (lemma5).

  • Definition 14, read literally. It is satisfied by no store with two replicas, so Theorems 6 and 12 would hold vacuously (Store.literalEC_false). It requires that every abstract execution that an infinite execution complies with be eventually consistent. Compliance (Definition 9) fixes only the per-replica operation sequences, so the abstract execution whose visibility is just the per-replica order always complies. In an infinite execution where two replicas read the same MVR forever and nothing is written, this abstract execution is correct and causally consistent but not eventually consistent. The proofs use "some correct abstract execution that the execution complies with is eventually consistent", which we adopt.

  • Theorem 12, bound. It claims n' lg k bits. The counting argument gives ⌊n' lg k⌋ (e.g. three distinct messages may have lengths 0, 1, 1). Its hypothesis "k ≥ min{n−2, s−1}" plays no role; we prove the bound for all k ≥ 1, and need n ≥ 3 and s ≥ 2 (otherwise n' ≤ 0).

Typos

  • Definition 18, condition 1 writes w'_i →vis w_{i-1}; the prose and the proof use w_{1-i}. Definition 18 also implicitly needs w_0 ≠ w_1.

Proof gaps in true statements (2)Theorem 12 · Lemma 5

🛠️ Theorem 12 (message size), the decoding argument

The sketch claims R_n "cannot return w_y" before it has received R_i's g(i)-th message "since R_n does not know this value", but m_g itself may carry R_i's writes.

Impact. Statement true (with ⌊n' lg k⌋ bits); saved by a different decoding argument (theorem12, Cx.key, Cx.decode, Cx.mg_injective).

Details

A store may piggyback everything it knows on m_g. The paper also never shows that R_n exposes w_y once it has the g(i)-th message, and defers both facts to the full version.

Repair

R_n receives only the first g(p) messages of every writer, and m_g. Its state is then final: it has heard everything sent in the sub-execution where every writer stops after g(p) rounds. So, by eventual consistency, its reads return exactly {1} from y and ⟨g(i), i⟩ from x_i. If m_g = m_{g'} with g(i) < g'(i), the same state of R_n arises in the g' execution. There R_{n-1} read ⟨g'(i), i⟩ before writing y, so causal consistency makes ⟨g'(i), i⟩, which overwrites ⟨g(i), i⟩, visible to R_n's read of x_i. (theorem12, Cx.key, Cx.decode)

🔧 Lemma 5 (hypothesis)

The hypothesis "e →hb w ⇒ e →rcv w for any do event e" cannot hold for earlier events of R itself, since a replica does not receive its own messages, so the lemma says nothing at its uses.

Impact. With a changed hypothesis the lemma holds (lemma5). We read it as: nobody has a message pending before w, and R has received every message sent by another replica.

Repair

The lemma is proved only in the full version; we give a proof. Insert an invisible read r before w and complete the execution quiescently. If R sent nothing after w, late reads at another replica would never see w, but by Lemma 3 they return what r returned. A late read at R sees w, so w is overwritten by some w₂ returned by r, while w₂ is visible to r and hence to w (Definition 4(2)). This is a visibility cycle. (lemma5)

The formalizationmodel, Lean names of the results, trust

Model.

  • n replicas (finite type ι), each a partial, possibly nondeterministic state machine (Store, Section 2); objects are multi-value registers; written values are arbitrary. Events: do(o, op, v), send(m) (broadcast), recv(m).

  • Asynchronous message passing, no failures. Messages may be lost, delayed, reordered and duplicated; an execution only requires that every receipt follows a send by another replica (IsExec, Definition 1). Infinite executions are considered only when sufficiently connected (SuffConnected, Definition 3).

  • Assumptions on stores, as in the paper: a send leaves nothing pending (SendClears), op-driven messages (OpDriven, Def. 15), invisible reads (InvisibleReads, Def. 16); and, made explicit, high availability (Available) and input-enabled receipts (RecvEnabled). The paper says both in prose and uses them, but never states them as properties of the transition function.

  • Abstract executions (AE, Def. 4) carry the total order H and visibility; MVR specification, correctness, causal and eventual consistency are Defs. 7, 8, 12, 13. Compliance (Def. 9) is "an abstract execution on the execution's own do-events with the same per-replica order" (AE.On), which is the same up to renaming events.

  • Store-level consistency: CausallyConsistent (every finite execution complies with a causally consistent abstract execution) and EventuallyConsistent P (every infinite sufficiently connected execution complies with a correct, eventually consistent abstract execution, in the model P) — the latter is Definition 14 with "some" for "every" (see above).

  • No randomness; all universal statements quantify over every store satisfying the hypotheses and every execution (adversarial scheduling and message delivery).
