import Mathlib /-! # Two-party impossibility over a fully-defective channel Theorem 3 of [CCGS22] (= Theorem 20 of the arXiv full version 2205.11148): *Fix a non-constant function `f(x, y)`. No two-party deterministic algorithm that gives output (or terminates) can compute `f` over a fully-defective channel.* [CCGS22]: K. Censor-Hillel, S. Cohen, R. Gelles, G. Sela, *Distributed Computations in Fully-Defective Networks*, PODC 2022. ## Model * Two parties, Alice (input `x : X`) and Bob (input `y : Y`), joined by one bidirectional channel; messages are drawn from an arbitrary alphabet `M`. * **Parties** (`Party`) are deterministic, event-driven state machines: a start-up event (`start`, depending on the input) and one event per received message (`recv`). At every event a party moves to a new state, sends a finite list of messages and may produce an output. Outputs are **irrevocable**: a party's output register (`Config.outA`, `Config.outB`) holds the *first* value it ever output. (Termination is a special case: a terminated party is one that never sends anything afterwards; the impossibility only needs the output requirement.) For the remark on revocable outputs we also keep the *latest* value output (`Config.estA`, `Config.estB`). * **Fully-defective channel**: the adversary may replace the content of every message by any element of `M`. It can neither create nor drop messages. Hence a configuration only records how many messages were sent and delivered in each direction; a delivery step (`Protocol.Step`) takes one in-transit message and hands it to its receiver with an adversarially chosen content `m : M`, in an adversarially chosen order (asynchrony). * **Executions** (`Protocol.IsFairExec`) are sequences `e : ℕ → Config` starting at the initial configuration in which every step is a delivery or a stutter (`e (n+1) = e n`), and which are **fair**: every message sent is eventually delivered. Stutters encode finite executions (which must end with no message in transit) and are harmless otherwise. * `Protocol.ComputesWithOutput P f`: for all inputs, in every fair execution both parties eventually output `f x y`. ## Main results * `Protocol.bob_fails` / `Protocol.alice_fails`: if `f` depends on Alice's (resp. Bob's) input, then for some inputs there is a fair execution in which Bob (resp. Alice) never outputs `f x y`. * `Protocol.theorem3`: no protocol computes a non-constant `f` and gives output. * `Protocol.exists_fairExec` (non-vacuity): every protocol has a fair execution on every input; `constProtocol_computes`: constant functions are computable with output. * `estimateProtocol_stabilizes`: the paper's remark — without the output requirement, the protocol "send `x` messages, then keep `f(x, #received)` as a revocable estimate" eventually stabilizes on `f x y` in every fair execution (`X = Y = ℕ`). ## Proof As in the paper. The executions used are those in which the adversary overwrites every message with a fixed `m₀`; then a party's state and output are functions of its input and the number of messages received so far (`Party.runState`, `Party.runOut`; this is the paper's sequence `B_y`). A round-robin scheduler (`Protocol.rr`) yields such a fair execution for all inputs. If `f x y ≠ f x' y`, Bob's first output on `y` is the same value `r̂` in both executions on `(x, y)` and `(x', y)` whenever he outputs at all (`Party.runOut_unique`), so it is wrong in one of them.
