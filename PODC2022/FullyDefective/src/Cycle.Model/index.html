import Mathlib /-! # Algorithm 1 of [CCGS22]: the content-oblivious simulator on a simple cycle (ring layer) K. Censor-Hillel, S. Cohen, R. Gelles, G. Sela. *Distributed Computations in Fully-Defective Networks.* PODC 2022 (full version arXiv:2205.11148). This file models the *ring layer* of Algorithm 1: the content-oblivious broadcast mechanism (token phase, Algorithm 1(a), and unary data phase, Algorithm 1(b)) on an oriented cycle `ZMod n`. The simulated protocol `π` is abstracted away: the queue `Q_u` of each node receives arbitrary positive payloads (`push`, an environment step that may happen at any time), and a node "decodes" one payload per epoch into its `log`. The composition with an actual protocol `π` is in `Cycle/Simulation.lean`. ## The network Node `u` is joined to `u + 1` (its clockwise neighbour) and to `u - 1` (its counterclockwise neighbour); for `n = 1` this is a self-loop and for `n = 2` a double link, the algorithm works verbatim there too. Messages are pulses (fully-defective channels: the content of every message may be corrupted, so content is ignored), hence a channel is a counter. We keep, for every node, the number of clockwise (`cw`) and counterclockwise (`ccw`) pulses it has sent and received: the clockwise pulses in transit to `u` are `cwS (u - 1) - cwR u`, the counterclockwise ones `ccwS (u + 1) - ccwR u`. Channels are not FIFO, which is irrelevant for indistinguishable pulses. ## The algorithm (one state per program point) * `idle` — line 1 (waiting for a non-empty queue or a clockwise `request` pulse); * `waitReq` — line 3 (own `request` sent, waiting for one); * `ready` — line 8 (waiting for a `token` (ccw) or the first `data` (cw) pulse); * `fwd c` — line 25 (non-holder in the data phase, `c` data pulses received and forwarded); * `send d r` — line 21 (token holder, sent its `d` data pulses, `r` of them came back); * `waitEnd d` — line 23 (token holder, `end` pulse sent). A node only reads a pulse from a direction it is waiting for (`cwReady`, `ccwReady`): pulses from the other direction stay in the incoming buffer, as in the pseudo-code's `wait until` statements. The meanings (`request`, `token`, `data`, `end`) are never stored in pulses: a node interprets a pulse by its direction and its own state only. ## Ghost state `Config.ds` (the payloads of the epochs started so far, in order) and `Config.hold` (the node that captured the token last, initially `T₀`) are ghost variables for the analysis; transitions never read them. -/ namespace
