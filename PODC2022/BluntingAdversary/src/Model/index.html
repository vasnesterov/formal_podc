import Papers.PODC2022.BluntingAdversary.MDP import Cslib.Computability.Distributed.SharedMemory.StrongLin /-! # Randomized programs using shared objects (Sections 2–4 of the paper) Attiya, Enea, Welch, *Blunting an Adversary Against Randomized Concurrent Programs with Linearizable Implementations*, PODC 2022 (arXiv 2106.15554v2). ## Programs (Section 2.3) A `Program P A C` gives every process `p : P` a deterministic client with states `C`; in every state the client either computes locally (`loc`), samples uniformly from a set of `m + 1` values (`rnd`, the paper's `random(V)`), invokes an operation `o` of the shared object `A` and continues with the response (`call o k`), or has terminated (`done`). A finite set of objects is modelled as one object whose operations are tagged with the object they belong to (the paper relies on the locality of its notions, Theorem 3.1, to do the same). ## Objects An object is used through an `ObjSem`: per-process local states `L`, a shared memory `M`, the local state after an invocation (or an immediate response, for atomic objects), and the next internal action of an invocation: a deterministic step on the memory, a uniform random choice (only used by the transformed objects `O^k`), or a return. * `implSem I Π`: a deterministic shared-memory implementation `I` (CSLib's `Impl`: base objects with sequential specifications accessed atomically, deterministic per-process code) together with a *preamble mapping*, given as the set `Π p l` of local states that are still inside the preamble of the current operation (Section 3: "`i` passed `Π(M)`" = the local state of the invocation is no longer in the preamble). * `atomSem A`: the atomic object with sequential specification `A` (every invocation returns in the same step). * `iterSem I Π k`: the preamble-iterating transformation `O^k` (Algorithm 2). ## Executions and adversaries (Section 2.4) `sys Pr O` is the game whose states are configurations (client states, which processes are inside an operation, object local states, memory) plus two ghost fields: the number of program random steps so far (`coins`) and a flag `badCoin` recording whether some program random step happened while some invocation was inside its preamble (i.e. the execution prefix ending with that random step was not complete w.r.t. `Π`).
